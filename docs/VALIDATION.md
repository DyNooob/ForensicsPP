# Forensics++ Validation

> Beta 6 capability: **public, reproducible parser validation** — not a unit-test alias.
> Validation answers: *known evidence → Forensics++ analysis → known expected forensic result*.

Status: **Foundation (beta.6)**. The harness and the first two core-direction cases
(Binary/File carving, SQLite deleted-record recovery) are live and runnable. More
core directions (EVTX / APK / PCAP / Firmware) are scaffolded below; their fixtures
and expected outputs are being added as those parsers are hardened.

## Run it

```bash
npm run validate              # runs tests/validation/*.test.ts via vitest
npm run validate:fixtures     # (re)generates tests/fixtures/* (deterministic)
```

`npm run validate` is a thin alias to `vitest run tests/validation` — it reuses the
existing test runner, no new harness. `npm run validate:fixtures` regenerates the
small, public, privacy-free fixtures under `tests/fixtures/` (committed for
inspectability; `expected.json` records the expected forensic outputs).

## How a validation case is built

Each case follows one chain:

```
fixture (deterministic, public, small)
   ↓
real Forensics++ analyzer (no mocks for the parser under test)
   ↓
assert expected forensic result (offsets / recovered rows / findings / artifacts)
```

The parser under test is the **same code the app ships** — e.g. `scanCarvableObjects`
(`src/features/file/carver.ts`) and `inspectSqliteDatabase` (`src/features/sqlite/forensic.ts`).
No second schema, no parallel result model.

## Cases

| Direction | Fixture | Parser | Expected | State |
|---|---|---|---|---|
| Binary / File carving | `embedded-signatures.bin` | `scanCarvableObjects` | signatures recovered at **exact source offsets** (provenance) | ✅ live |
| SQLite deleted-record | `sqlite-deleted-record.sqlite` | `inspectSqliteDatabase` | deleted row recovered from free space; envelope emits `sqlite-recovery` finding + artifact + `SQLITE_RECOVERY_HEURISTIC` limitation | ✅ live |
| EVTX | — | `inspectEvtx` (planned) | records aggregated by channel/level/event id; known record id present | ⏳ scaffold |
| APK | — | `parseAndroidManifest` (planned) | declared permissions / signing state match fixture manifest | ⏳ scaffold |
| PCAP | — | `analyzePcap` (planned) | known session/flow count + IOC extraction | ⏳ scaffold |
| Firmware | — | `analyzeFirmware` (planned) | carved object at known offset + signature | ⏳ scaffold |

## Fixture policy

- **Public / privacy-free / no copyright risk.** Generated by script (`gen-validation-fixtures.mjs`)
  or minimal hand-built bytes — never real case data.
- **Small.** All fixtures are < 16 KiB.
- **Deterministic.** `gen-validation-fixtures.mjs` produces byte-identical output.
- **Self-documenting.** `tests/fixtures/expected.json` records the expected forensic result
  next to each fixture.

## What validation is NOT

- Not a replacement for `vitest` unit tests of internal helpers (`parseHeader`, `parseFrame`, …).
- Not a claim of completeness: a PASS here means *this known evidence produces this known
  result*, not that the parser handles every malformed input.
- Not a substitute for manual examiner review of evidentiary output.

## Adding a case

1. Add a fixture (generate it in `gen-validation-fixtures.mjs` or hand-build bytes).
2. Record expected output in `tests/fixtures/expected.json`.
3. Add `tests/validation/<direction>.test.ts` that drives the real analyzer and asserts the
   expected result.
4. Run `npm run validate`.
